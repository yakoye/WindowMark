# 窗口拖动 — 设计

日期：2026-09-03
来源：希望有 AltDrag / AltSnap 那样的「按住修饰键 + 拖动鼠标移动窗口」

---

## 背景与许可证前提

参考对象是 [AltSnap](https://github.com/RamonUnch/AltSnap)（AltDrag 的 fork）。

**它是 GPL-3.0，因此不移植它的任何代码。** GPL-3.0 是强 copyleft：把它的代码合并进来，
整个 WindowMark 必须以 GPL-3.0 发布，且撤不回来。WindowMark 在 v0.4.7 刚发了 MIT，正是
为了保住「可以自由使用、修改、闭源、商用」这个自由度。

而且要的功能本身并不复杂：低级鼠标钩子 + 修饰键判断 + `SetWindowPos`。AltSnap 那 30–40 个
源文件里绝大部分是不需要的东西（边缘吸附、透明度调节、滚轮切窗口、几十个配置项、自己的
配置文件格式和 GUI），把那些融进一个 C++ 项目比自己写核心功能工作量还大。

**结论：完全自己实现，不读也不抄 AltSnap 的源码。**

---

## 功能范围

- **左键拖 = 移动窗口**
- **右键拖 = 缩放窗口**（按鼠标在窗口内的位置决定拉哪条边/角）
- 触发键可配置，见下

**明确不做**（AltSnap 有但这里不要）：

- 边缘吸附 / 窗口间自动对齐
- 「主副动作调换」（左右键动作互换）
- 「使用组合键激活」（要求同时按住全部勾选键，而非任一）
- 透明度调节、滚轮切窗口、以及 AltSnap 的其余配置项

## 触发键：六个复选框，任一命中即触发

设置界面给六个独立复选框，勾中的**任意一个**按住即可触发（不是组合）：

```
□ 左Alt    □ 左Win    □ 左Ctrl
☑ 右Alt    □ 右Win    □ 右Ctrl
```

默认只勾**右 Alt**。左右可区分是因为 Windows 本来就有独立虚拟键：`VK_LMENU`/`VK_RMENU`、
`VK_LWIN`/`VK_RWIN`、`VK_LCONTROL`/`VK_RCONTROL`。

配置文件：

```ini
drag.enabled=false
drag.modifiers=RAlt        # 多个用 | 分隔，任一按住即触发：RAlt|LWin
```

六个预设键名为 `LAlt RAlt LWin RWin LCtrl RCtrl`。**另外允许在配置文件里写任意键名**，
复用 `src/core/Hotkey.cpp` 已有的键名表（`pin.hotkey` 正在用它）。设置界面只呈现那六个
复选框；配置文件里写的额外键，界面读得懂、照常保留，不会被覆盖掉。

## Win 键：键盘钩子按需安装

Win 键有个特有问题：**按下再松开会弹出开始菜单**，哪怕中间做了别的事。要压掉它得装
`WH_KEYBOARD_LL` 并吞掉那次 keyup。

**只有当配置里勾了左 Win 或右 Win 时才安装键盘钩子。** 只用 Alt / Ctrl 的用户全程只有一个
鼠标钩子。键盘钩子比鼠标钩子更敏感（杀毒软件更关注、出错影响更大），不该让所有人默认承担。

## 行为决定

### 拖鼠标底下的窗口，不是活动窗口

按下修饰键时鼠标指向哪个窗口就拖哪个，**且不需要先激活它**。这正是 AltDrag 好用的原因：
可以把背景窗口挪开而不打断当前的焦点。

### 最大化的窗口先还原再拖

与 Windows 拖标题栏的既有行为一致。还原后窗口应当跟着光标走，而不是跳到原来的还原位置。

### 实时移动，不画虚线框

项目已有高频窗口几何更新的经验（边框每次几何变化都要重定位），做得到实时。虚线框是
Win9x 时代的做法，视觉上过时。

### 缩放拉哪条边：九宫格

把窗口按 **1:1:1 等分**成 3×3，鼠标按下时落在哪一格就决定拉哪条边或哪个角：四角拉两条边，
四边拉一条，正中间则等同于移动（否则中间按下无事可做）。这是纯几何判断，放 core 并单测——
边界值（正好落在格线上、窗口极窄导致格子退化）最容易写错。

缩放有**最小尺寸下限**：宽高各不小于 `GetSystemMetrics(SM_CXMINTRACK/SM_CYMINTRACK)`，
低于此值就停在下限而不是继续缩。否则窗口会被拖成一条线甚至反转。

### 拖动中途松开修饰键

**以鼠标键为准**：修饰键先松开、鼠标键还按着时，拖动继续到鼠标键松开为止。反过来，鼠标键
先松开就结束，此后单独按修饰键不做任何事。这符合手上的直觉——手指离开 Alt 不代表要放弃
正在拖的窗口。

### 两个必须吞掉的事件

和 Win 键弹开始菜单是同一类问题：**手势用掉的输入不能再传给应用**。

- **右键抬起**：右键拖动结束时若把 `WM_RBUTTONUP` 放行，应用会当成一次右击并弹出上下文
  菜单。必须在钩子里吞掉这一次抬起。
- **Win 键抬起**：见上文，只在勾了 Win 键时才有这个问题，也才装键盘钩子。

只吞「确实被手势用掉」的那一次：没有触发拖动时，一切事件原样放行。

## 分层

沿用项目现有做法：纯计算进 `windowmark_core`（`windowmark_core_tests` 只链接它），系统
调用留平台层。

| core（可单测） | platform（`WinDragBackend`） |
|---|---|
| 修饰键字符串 ↔ 键码的解析与格式化 | 装/卸 `WH_MOUSE_LL`、按需装 `WH_KEYBOARD_LL` |
| 「按下的键里有没有命中配置」 | `GetAsyncKeyState` 读键状态 |
| 九宫格 → 拉哪条边 | `SetWindowPos` 实际移动/缩放 |
| 拖动位移 → 新的窗口矩形 | 命中测试找鼠标下的窗口 |

这几样正是最容易写错、又最难靠肉眼验证的部分——尤其九宫格边界和缩放时的矩形计算。

## 性能：钩子里只走最短路径

`WH_MOUSE_LL` 是全局钩子，**每一次鼠标移动都会调用它**，而且是在安装它的线程上同步处理。
处理慢会拖累整个系统的鼠标手感。

**钩子的第一件事就是查修饰键**（`GetAsyncKeyState`，量级几十纳秒），没按住就立刻
`CallNextHookEx` 返回，不做任何其他事——不查窗口、不算几何、不碰配置。只有已经在拖动
或刚刚判定要开始拖动时才走完整逻辑。

实现后实测钩子在空闲路径上的耗时，写进 `VALIDATION.md`。这是硬指标，不是感觉。

## 排除应用

有些程序自己就用 Alt+拖动做别的事（Photoshop 等）。钩子会把这些事件吞掉，所以需要排除名单。

**复用 `border.excluded_apps` 那一套**：同样的选择面板、同样的 exe 路径键。配置项独立：

```ini
drag.excluded_apps=<exe 路径列表>
```

与 `border.excluded_apps` / `selection.disabled_apps` 分开——不想要边框、不想要书签、不想要
拖动是三件不同的事。

子菜单：

```text
窗口拖动 >
  ✓ 启用窗口拖动
    排除应用...
    ──────
    拖动设置...      ← 六个修饰键复选框在这里
```

顶层「窗口拖动」左边跟其他三个功能一样显示启用状态的对勾（只读，切换在子菜单第一项——
`MF_POPUP` 项没有命令 ID，无法兼作开关）。

**「暂停所有」包含窗口拖动**：它和书签/边框/置顶一样是 WindowMark 自己的功能，暂停时应当
连钩子一起卸掉。（剪贴板守护不在其列，那是独立进程，理由见它自己的 spec。）

## 已知风险

1. **全局鼠标钩子拖慢系统**。用最短路径缓解，并实测耗时。若空闲路径耗时超过约 50µs
   需要重新设计。
2. **与应用自身的 Alt+拖动冲突**。用排除名单解决，文档写明。
3. **杀毒软件对低级钩子的反应**。鼠标钩子很常见（几乎所有截图工具都用），键盘钩子更敏感
   ——这正是它按需安装的另一个理由。
4. **合成鼠标事件的自动化测试会真的移动光标**。测试脚本必须先打招呼再跑。
