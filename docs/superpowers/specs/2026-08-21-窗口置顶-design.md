# 窗口置顶 — 设计

WindowMark 的第三个功能。前两个是「书签」和「窗口边框」，三者共用一个托盘进程、一套
WinEvent 钩子和一个 Coordinator，彼此不依赖。

## 目标

把任意顶层窗口固定在其他窗口之上，并且**让人一眼看出哪些窗口被固定了**。

置顶功能最常见的失败方式不是钉不住，而是钉住之后看不出来——过一会儿用户自己都忘了钉过
什么，只觉得某个窗口莫名其妙一直挡在前面，还找不到取消的地方。所以「可见」和「可管理」
和「能钉住」是同等重要的需求，不是锦上添花。

## 非目标

以下都是 PowerToys 有而这里**刻意不做**的，它们不属于「置顶」：

- 调节窗口不透明度
- 置顶时播放提示音
- 游戏模式检测
- 跨会话持久化（理由见「状态模型」）

## 设计原则

**对其他应用零侵入。** 不注入 DLL、不修改别人的代码、不猜别人的界面几何。这是整个项目
一以贯之的约束，置顶功能不破例。唯一作用于目标窗口的操作就是 `SetWindowPos` 设置
`WS_EX_TOPMOST`——那是功能本身，绕不开。

这条原则直接淘汰了 DeskPins 式的「在标题栏画一个图钉按钮」：它要在别人的窗口上画东西，
还得猜人家的按钮位置。实测数据见「已验证的事实」第 2 条。

## 架构

```
core/
  PinRegistry          纯逻辑：谁被钉住、原本是什么状态。无 Win32 依赖，可单测
  IPinBackend          新接口，与 IBorderBackend / IOverlayBackend 平级
  BorderModel          新增 pinned 标志
platform/windows/
  WinPinBackend        SetWindowPos 置顶 + 四种触发入口
```

### 接口

```cpp
// core/PinRegistry.h —— 纯逻辑，无 Win32
class PinRegistry {
public:
    // 返回 false 表示这个窗口已经在集合里，调用方不应重复记录原始状态
    bool Add(WindowId id, bool wasTopmostBefore);
    // 移出集合，并告诉调用方它原本是不是置顶的
    std::optional<bool> Remove(WindowId id);
    [[nodiscard]] bool Contains(WindowId id) const;
    [[nodiscard]] std::vector<PinRecord> Snapshot() const;
    // 清空并返回全部记录，供退出时逐个还原
    std::vector<PinRecord> Drain();
};

// core/Interfaces.h
class IPinBackend {
public:
    virtual ~IPinBackend() = default;
    virtual bool Start(const Settings& settings, PinCallbacks callbacks) = 0;
    // 真正去改目标窗口的 WS_EX_TOPMOST，返回改之前它是不是置顶的
    virtual std::optional<bool> SetTopmost(WindowId id, bool topmost) = 0;
    // 被钉住的集合变了，后端据此刷新系统菜单勾选和托盘菜单
    virtual void Apply(const std::vector<PinRecord>& pinned) = 0;
    virtual void UpdateSettings(const Settings& settings) = 0;
    virtual void Stop() noexcept = 0;
};

// 四种入口发起的请求都归一到这一个回调
struct PinCallbacks {
    std::function<void(WindowId)> onTogglePin;
    std::function<void()> onUnpinAll;
};
```

后端不自己维护状态，只上报意图；Coordinator 是唯一决定「钉还是取消」的地方。

### 谁画边框

**边框后端是唯一画边框的地方。** `WinPinBackend` 不画任何像素，它只负责两件事：维护
「哪些窗口被钉住了」，以及提供触发入口。状态交给 Coordinator，由 Coordinator 合成
`BorderModel`——每个窗口一个模型，带 `active` 和 `pinned` 两个标志，边框后端按
**置顶优先**挑颜色和线宽。

这样只有一条渲染路径，不会出现同一个窗口被画两圈边框，也不需要两个后端互相协调层级。

### border.enabled 的含义收窄

原来它是「画不画边框」，现在是「**普通窗口**画不画边框」。被钉住的窗口无论这个开关是
什么都画高亮边框。

这是刻意的：置顶功能必须自成一体，单独打开就能用。如果它的视觉提示依赖另一个默认关闭的
功能，那么用户按下快捷键之后屏幕上什么都不会发生——窗口确实置顶了，但看不出来。

## 状态模型

### 只在本次运行内有效

`HWND` 没有可靠的跨会话标识。这个项目已经为书签重命名和按窗口选择做过同样的判断，置顶
没有理由不一样。**不写入 `settings.conf`。**

### 退出时全部还原

WindowMark 退出时（正常退出、卸载器请求退出、设置对话框里关闭功能）必须把所有置顶窗口
还原。否则用户关掉程序之后，屏幕上留着几个浮在最前面的窗口，而**能取消它们的工具已经
没了**——用户只能逐个重启那些应用。

### 记录的是原始状态，不是布尔值

目标窗口可能本来就是置顶的（任务管理器自己有「置于顶层」选项，很多播放器也有）。所以
`PinRegistry` 存的是每个窗口**被我们接管之前的 topmost 状态**，取消时还原成原样，而不是
无脑设 `HWND_NOTOPMOST`——那会把人家自己开的置顶给关掉。

```cpp
struct PinRecord {
    WindowId id;
    bool wasTopmostBefore;   // 我们接管之前它就是置顶的吗
};
```

## 触发方式

四种入口，各自补位。全部零侵入。

### 1. 标题栏右键 →「置于顶层」

最符合直觉，也是 PowerToys 的做法。不注入即可实现，机制分两步：

**插入**：挂 `EVENT_SYSTEM_MENUPOPUPSTART` 钩子。`idObject == OBJID_SYSMENU` 时记下是哪个
窗口，`GetSystemMenu(hwnd, false)` 拿到菜单，`InsertMenuItemW` 插在 `SC_CLOSE` **前面**
（即「关闭」上方）。已置顶的窗口带 `MFS_CHECKED` 打勾。

**收点击**：`WM_SYSCOMMAND` 进的是目标应用自己的窗口过程，我们收不到。改用
`EVENT_OBJECT_INVOKED`——**这个事件的 `idChild` 字段带的就是菜单命令 ID**：

```cpp
if (data->idChild != kPinMenuCommandId) return;
```

**命令 ID 撞车防护**：插入前检查该 ID 是否已被目标应用自己的菜单项占用。占了就跳过并记
日志，绝不覆盖别人的菜单项。

**覆盖范围有限**：WinUI/UWP 窗口没有系统菜单，这条路对它们完全不适用。所以它不能是唯一
入口。

### 2. 准星抓取（主力）

覆盖**所有**应用，包括没有系统菜单的。两个入口共用同一套代码：

- **快路径**：左键按住托盘图标往外拖，超过拖动阈值后进入准星模式
- **稳路径**：托盘菜单 →「抓取窗口置顶...」，点一下进入准星模式，再点目标窗口

需要拖动阈值，否则单击托盘图标会变成「把光标底下的窗口钉住」，误触代价太大。

实现：`SetCapture` 到**我们自己的**窗口，光标换成十字准星，`WM_MOUSEMOVE` 时用
`WindowFromPoint` + `GetAncestor(GA_ROOT)` 找光标下的顶层窗口，`WM_LBUTTONUP` 时置顶它。
全程只读目标窗口，不给它发任何消息。

**实时预览**：划过哪个窗口，就给它临时画一圈置顶色的边框——直接复用边框渲染。DeskPins
只能改鼠标指针，我们能直接把目标框出来。

托盘图标可能被折叠在溢出区里，那种情况下「从图标拖出来」很别扭，所以菜单入口是必需的，
不是可有可无的备选。

### 3. 托盘子菜单

现有托盘菜单已有「书签」「窗口边框」两个子菜单，这里加第三个，与它们平级：

```text
WindowMark
书签              >
窗口边框           >
窗口置顶           >   ← 新增
──────────
暂停所有
开机启动
关于
──────────
退出
```

「窗口置顶」子菜单的内容：

```text
✓ 启用窗口置顶
  抓取窗口置顶...              ← 进入准星模式
  ──────────
✓ pcie register lists.xlsx    ← 已置顶的窗口，点击取消
✓ 计算器
  全部取消置顶
  ──────────
  边框颜色      >              ← 红 / 蓝 / 绿 三个快捷项
  置顶设置...
```

没有窗口被置顶时，中间那段和「全部取消置顶」都不显示。

这是「我到底钉了些什么」的出口，也是功能的发现入口——纯快捷键的功能等于没有说明书。

菜单宽度不受影响：「窗口置顶」和「窗口边框」同为四个字，而 Win32 菜单的宽度就等于最长
那一项的文字宽度。

### 4. 可配置快捷键（默认不设）

`RegisterHotKey` 全进程独占，谁先注册谁赢，后来的**静默失效**。这是这个项目此前去掉
Ctrl+Alt+W 的原因，那个理由依然成立。因此：

- 默认**空**，装完不抢任何按键
- 设置里按下即录，不用手填字符串
- **注册失败当场报出来**：「Ctrl+Alt+T 已被其他程序占用，换一个」。绝不允许「设了但没
  生效」这种状态存在，那比没有更糟
- 不默认 Win+Ctrl+T——那是 PowerToys 自己的置顶键，装了 PowerToys 的人一上来就撞

这是四种入口里唯一会波及其他应用的，所以默认关着，由用户显式开启。

## 视觉表现

复用边框渲染，置顶状态用独立的颜色和线宽：

- 颜色默认**红色 `#E74C3C`**。它要表达「这个窗口和别的不一样」，红色最不容易和现有的
  活动/非活动蓝紫色（`#6274E7` / `#7080AA`）混淆
- 线宽默认 **6px**，比普通边框的 4px 粗
- 托盘子菜单里放红/蓝/绿三个常用色快捷项，设置里是自由的 `#RRGGBB` 输入框

## 设置项

```
pin.enabled=true
pin.color=#E74C3C
pin.width=6
pin.show_in_system_menu=true
pin.hotkey=
```

`pin.hotkey` 默认空。其余与现有设置的读写方式一致，写入 `settings.conf`。

**注意**：被钉住的窗口列表**不在**这里——它是运行期状态，见「状态模型」。

## 边界情况

| 情况 | 行为 |
|---|---|
| 置顶的窗口被关闭 | `EVENT_OBJECT_DESTROY` 已在监听，从注册表移除 |
| 置顶的窗口最小化 | 保持置顶状态，恢复后依然置顶（与 PowerToys 一致） |
| 目标本来就是置顶的 | 记录原始状态，取消时还原为原样 |
| WindowMark 退出 | 全部还原为原始状态 |
| 菜单命令 ID 已被占用 | 跳过插入，记日志，不覆盖 |
| 窗口在排除列表里 | 复用 `tracking.exclude_classes`，不参与置顶 |
| 关闭「启用窗口置顶」 | 与退出同样处理：全部还原。功能关掉了却留下钉住的窗口，就再没有取消它们的地方 |
| 同一个窗口被重复置顶 | `PinRegistry::Add` 返回 false，不覆盖已记录的原始状态 |
| 多个置顶窗口的相对顺序 | 系统不保证。Citrix、RDP、VMware 的窗口可能盖住置顶窗口，这是 Windows 的限制，PowerToys 文档亦有同样说明 |

## 测试策略

**Core 层**（进现有的 `windowmark_core_tests`，无 Win32 依赖）：

- `PinRegistry` 的加/删/查/清空
- 原始 topmost 状态的记录与还原
- 重复置顶同一个窗口不应覆盖已记录的原始状态

**平台层**（脚本化验证，不靠肉眼）：

- 跨进程置顶的往返：设置 → 读 `WS_EX_TOPMOST` 位确认 → 取消 → 确认还原
- 系统菜单项：插入后用 `GetMenuItemCount` / `GetMenuStringW` 核对文字与位置在 `SC_CLOSE`
  之前；已置顶时核对 `MFS_CHECKED`
- 退出还原：钉住若干窗口 → 结束进程 → 逐个核对 topmost 位已还原
- 托盘子菜单：用 `WM_COMMAND` 驱动，`MN_GETHMENU` 读菜单项核对

## 建议的实施顺序

分三段，每段都能独立跑起来并验证，不必等全部做完才可用：

1. **能钉住、看得见。** `PinRegistry` + `BorderModel.pinned` + 边框后端按优先级选色 +
   托盘子菜单（启用开关、已置顶列表、全部取消）+ 退出还原。这一段做完功能就能用了。
2. **准星抓取。** 托盘拖拽与菜单入口、`SetCapture` 流程、实时预览高亮。
3. **标题栏菜单与快捷键。** 三个新 WinEvent 事件、菜单项插入与撞车防护、快捷键录制与
   注册失败提示。

第 1 段是地基；2 和 3 都只是往 `onTogglePin` 上再接一根线，彼此独立，顺序可换。

## 已验证的事实

以下三条都是本次设计前实测得到的，不是推断。

**1. 跨进程置顶可行。** 对另一个进程的窗口 `SetWindowPos(HWND_TOPMOST)` 返回真，且
`WS_EX_TOPMOST` 位确实被设上（False → True → False）。

这一条需要验证，是因为同期排查拖动卡顿时发现：**非前台进程发起的层级抬升会被系统静默
忽略**（返回 TRUE、什么都不做）。实测确认那条限制管的是「在同一层里往上抬」，不管「设置
置顶样式」。

**2. 标题栏按钮几何不可靠——所以不做图钉按钮。** `DWMWA_CAPTION_BUTTON_BOUNDS` 实测
13 个窗口：

| 应用 | 结果 |
|---|---|
| notepad++ / explorer / Feishu / InputScope | 185x37，可用 |
| Claude、ChatGPT（Electron） | 宽度为 0 |
| PowerToys、设置（WinUI） | 全 0 或没有 |

规律：用系统非客户区的应用能查到，自绘标题栏的查不到。真实应用窗口里约一半失败。
DeskPins 是 2000 年代的工具，那时候标题栏还都是系统画的。

**3. 系统菜单可以跨进程插入。** 13 个窗口里 9 个 `AppendMenu` 成功（chrome、claude、
explorer、ChatGPT、Typora、notepad++、ApplicationFrameHost）。失败的 4 个
（SystemSettings、PowerToys.QuickAccess、TextInputHost）是**压根没有系统菜单**，不是被
拒绝。
