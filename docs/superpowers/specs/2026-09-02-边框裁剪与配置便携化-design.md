# 边框裁剪与配置便携化 — 设计

日期：2026-09-02
来源：一位使用者的两条反馈

---

## 背景

反馈原文要点：

1. 双屏下 Office 三件套最大化时，边框会显示到另一块屏上。建议「最大化时不显示边框」。
2. C 盘装了还原工具，重启后 `%LOCALAPPDATA%\WindowMark\settings.conf` 被还原。建议配置文件便携化，或让用户指定配置文件路径。

两条都成立，但**第 1 条给出的解法不该采纳**，第 2 条的痛点比表面看到的更棘手。下面分别说明。

---

## 问题一：边框跨屏溢出

### 现象

窗口在左屏最大化时，边框的一部分画到了右屏上。

### 实测数据

用资源管理器做对照（单屏 1920×1080，工作区 1920×1020）：

| 状态 | `GetWindowRect` | DWM 扩展边界 | 两者之差 |
|---|---|---|---|
| 还原 | (691,162)-(1854,892) | (699,162)-(1846,884) | 左8 上0 右8 下8 |
| **最大化** | (-9,-9)-(1929,1029) | **(0,0)-(1920,1020)** | 左9 上9 右9 下9 |

关键：**最大化时 DWM 扩展边界正好等于工作区**。

### 根因

边框画在 DWM 边界外 `reach` 像素，`reach = max(0, border.width + border.offset)`，当前配置为 `4 + (-1) = 3`。

所以最大化时边框矩形是 **(-3,-3)-(1923,1023)**：

- 单屏：超出屏幕的部分被裁掉，看不见，所以从来没人发现
- 双屏：右边那 3px 越过分界线，**落在隔壁屏幕上**

这不是坐标算错，是「向外扩 `reach` 像素」这个设计没有考虑「窗口边缘就是屏幕边缘」的情况。

**同一根因也影响半屏吸附**（Win+←）：贴着屏幕分界的那条边同样会越界。所以修法不能只针对最大化。

### 为什么不采纳「最大化时不画边框」

1. 最大化窗口的边框不是没有意义的——双屏各有一个最大化窗口时，**活动/非活动的配色正是用来区分焦点在哪边**的。
2. 置顶高亮会一起消失。最大化窗口被置顶后将失去唯一的视觉反馈（这与 `border.enabled` 关闭时仍为置顶窗口画边框的既有约定冲突）。
3. 它只挡住最大化这一种情况，半屏吸附的越界依旧存在。

用一个功能缺失去掩盖坐标越界，是把问题藏起来而不是解决它。

### 方案：逐边夹取到监视器内

在边框窗口的外矩形算好之后、定位之前，逐边夹取：

```
mon   = MonitorFromRect(窗口 frame, MONITOR_DEFAULTTONEAREST) 的 rcMonitor
reach = max(0, border.width + border.offset)

对左边：gap = frame.left - mon.left
        若 0 <= gap <= reach  则  outer.left = max(outer.left, mon.left)
对上边：gap = frame.top - mon.top          同上
对右边：gap = mon.right - frame.right      同上，取 min
对下边：gap = mon.bottom - frame.bottom    同上，取 min
```

**条件为什么是 `0 <= gap <= reach`**，而不是「相等」或只有上界：

| 场景 | 左 | 上 | 右 | 下 | 结果 |
|---|---|---|---|---|---|
| 最大化 (0,0)-(1920,1020) | 0 → 夹 | 0 → 夹 | 0 → 夹 | 60 → 不夹 | 三边收进屏内；底边落在任务栏区域，被任务栏遮住，无害 |
| 半屏吸附 (0,0)-(960,1020) | 0 → 夹 | 0 → 夹 | 960 → 不夹 | 60 → 不夹 | 贴边的收进去，中间那条正常外扩 |
| 手动横跨两屏 | −420 → **不夹** | — | 1340 → 不夹 | — | 完全不受影响 |

下界 `0 <=` 是关键。横跨两屏时窗口边缘落在监视器**外面**（gap 为负），没有下界就会被误裁，那是一个回归。

用 `MonitorFromRect` 而不是 `MonitorFromWindow`：不依赖 HWND 此刻是否仍然有效。

### 落点

改在 `WinBorderBackend` 的 `BorderWindow::OuterRect()` 返回前：

- 监视器是平台概念，`windowmark::Coordinator` 不该知道
- `BorderModel::frame` 应当保持窗口的真实几何，裁剪属于渲染细节

`WinUtil.cpp` 中 `WorkAreaFor()` 已在使用监视器 API，无需引入新依赖。

**几何判断本身提取成 core 的纯函数** `ClampBorderToMonitor(frame, outer, monitor, reach)`，放在新文件 `src/core/BorderGeometry.cpp`。这不违反上面两条：该函数只收四个 `Rect` 和一个整数，不认识 `HMONITOR`，`Coordinator` 不调用它，`BorderModel` 也不变。这么放的唯一理由是**可测**——`windowmark_core_tests` 只链接 `windowmark_core`，逻辑留在平台层就进不了单测，而「下界 `0 <=` 不能省」这条正是最需要被测试钉死的地方。`MonitorFromRect` / `GetMonitorInfoW` 这两个系统调用仍然留在 `WinBorderBackend`。

## 问题二：配置文件位置

### 痛点的真相

反馈者的场景是「C 盘有还原工具」。顺着推下去会得到一个反直觉的结论：

**把配置文件挪到 exe 同目录，救不了他。**

因为 WindowMark 默认装在 `C:\Users\<用户>\AppData\Local\Programs\WindowMark\`——跟配置文件一样在 C 盘，会被一起还原。

同理，「让用户指定配置文件路径」这个功能也救不了他。这条信息不可能存在配置文件自身里（得先找到配置文件才能读它），只能存在：

| 存哪 | 对还原工具场景 |
|---|---|
| 注册表 `HKCU` | 在 C 盘，一样被还原 |
| exe 同目录的指针文件 | 程序在 C 盘，一样被还原 |
| 命令行参数 | 不落盘，但要改快捷方式；U 盘双击 exe 即失效 |

**结论：对还原工具场景，唯一可靠的解是把整个 WindowMark 目录搬到非 C 盘运行。** 任何留在 C 盘的指针都会跟着被还原。这一点必须写进用户文档，否则用户会以为改个设置就完事了。

配套提醒：搬走之后如果 C 盘的安装版还在，两个实例会因单例互斥量 `kSingletonMutex` 冲突，第二个直接退出。所以是「搬走」，不是「多放一份」。

### 方案：三层查找

```
1. exe 同目录的 settings.conf              存在即用（便携，跟着程序走）
2. HKCU\Software\WindowMark\ConfigPath     本机显式指定
3. %LOCALAPPDATA%\WindowMark\settings.conf 默认（现状）
```

`AppIdentity.h` 目前只有系统的 Run / Uninstall 键，没有产品自己的注册表根，需要新增 `Software\WindowMark`。值 `ConfigPath` 为 `REG_SZ`，存配置文件的完整路径（含文件名）；值不存在或为空字符串等同于「未指定」。

**为什么便携排在显式指定之前**：注册表跟着**机器**走，exe 同目录的 conf 跟着**程序**走。U 盘插到别人电脑上，不应该去读那台机器注册表里指向的本地路径。

代价是可能反直觉——用户指定了路径，却因为 exe 旁边有个 conf 而没生效。**因此设置界面必须显示当前实际生效的那一个**，让优先级可见。

### 设置界面

托盘菜单在「开机启动」下方新增「配置文件...」，打开一个小对话框：

```
当前生效：C:\Users\color\AppData\Local\WindowMark\settings.conf   （默认位置）

○ 默认位置   %LOCALAPPDATA%\WindowMark\
○ 程序目录   <exe 所在目录>          便携，跟着程序走
○ 自定义     [____________________] [浏览...]
```

三个选项正好是三层查找的显式表达，不引入第四种概念。选「程序目录」即在 exe 同目录创建 `settings.conf`。

### 两个必须处理的细节

**切换位置时要搬数据。** 否则用户一改设置，配置就"没了"。做法：把当前配置内容写入新位置，旧文件保留不删。

**保留旧文件会与优先级打架。** 若当前是便携模式（exe 旁边有 conf），用户改成「自定义 `D:\x`」，下次启动第 1 层又会把 exe 旁边那个选回来，设置等于没生效。因此**从便携切走时，把 exe 同目录的 `settings.conf` 改名为 `settings.conf.disabled`**——不删数据，也不会再被探测到。

**路径失效**：分两个时机各校验一次。

- **对话框里选中某一项时**立即试写目标目录，不可写就当场拒绝并说明原因，不要等到用户按下确定、配置搬过去之后才发现存不进去。
- **启动查找时**若选中的位置已不可用（U 盘拔了、目录被删、变成只读），回落到默认位置并明确提示，不得静默失败。

装在 `C:\Program Files\` 这类只读位置时，静默保存失败比回落更糟——用户会以为设置生效了。

---

## 明确不做的

- **不加「最大化时不画边框」开关。** 裁剪后那条线贴着屏幕边缘、视觉克制，先看实际效果。真有人要再说。
- **不把被排除应用的路径改成相对路径。** 配置文件里没有任何指向 WindowMark 自身的路径；带路径的 `border.excluded_apps` 和 `selection.disabled_apps` 记录的是**其他应用**的 exe 路径（Chrome、Typora 等），与 WindowMark 装在哪没有相对关系。

---

## 已知限制（需写入用户文档）

1. **换机器后应用排除会静默失效**。`border.excluded_apps` / `selection.disabled_apps` 按 exe 绝对路径标识应用，换一台机器路径不同，这两项匹配不上（不报错，等于没排除）。这是按 exe 路径做标识的固有代价——也正是它能把「墨鱼阅读」和 Chrome 分开的原因，两者类名同为 `Chrome_WidgetWin_1`。
2. **便携模式下开机自启动会因盘符变化失效**。Run 键写的是当时的绝对路径，U 盘换机器盘符一变就指不到了。

---

## 验证方式

**边框裁剪**

- 最大化：边框四边均不超出所在监视器（底边允许落入任务栏区域）
- 半屏吸附：贴边的三条边收进屏内，中间那条仍外扩 `reach`
- 手动横跨两屏：边框与修改前逐像素一致（无回归）
- 普通窗口：仍为 `3,3,3,3`

**配置位置**

- 三层查找各自命中，且「当前生效」显示与实际读取的文件一致
- 便携 → 自定义：旧文件被改名为 `.disabled`，重启后仍用自定义路径
- 指定到只读目录：回落默认位置并提示
- 切换后配置内容不丢
